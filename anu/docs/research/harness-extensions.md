# Harness inventory for extensions

HARNESS INVENTORY FOR AN ANU EXTENSION SYSTEM (read-only research; paths are relative to (local path)

(1) WHAT ALREADY EXISTS: INSTALL, ENABLE, DISABLE, AUTHOR

Plugins (the unit that bundles everything):
- Layout and contract: plugins/README.md and skills/plugin-builder/references/plugins.md. A plugin is `<workspace>/plugins/<name>/` with a `package.json` (it needs a `peerDependencies["@anu/plugin-api"]` range) or a standard `plugin.json`. It can contribute these surfaces: `hooks/*.ts`, `tools/*.ts`, `skills/<id>/SKILL.md` (with an optional `TOOLS.json` for tools scoped to that skill), `schedules/`, `mcp.json` (Agent Plugins 1.0.0 format, see assistant/src/plugins/mcp-servers.ts; its tools appear as `mcp__<id>__<tool>`), `routes/` (served under `/x/plugins/<name>/`), `channels/ingress.json` and `apps/`. In package.json it can also declare `credentialKeyPatterns` and `vellum.artifact`.
- Loader: assistant/src/plugins/user-loader.ts, then mtime-cache.ts (`populateCacheAtBoot`, `reconcilePluginSourcesNow`), external-plugin-loader.ts, installed-plugin-dirs.ts (realpath containment), hooks/hook-loader.ts. A plugin that fails to load is skipped without affecting the others, and there is a 10 s import timeout.
- Plugin API: the package name is in plugin-api-package.ts (`@anu/plugin-api`, with the legacy `@vellumai/plugin-api` also accepted). ensure-plugin-api-shim.ts writes a shim package into the workspace, and ensure-shared-dep-links.ts links shared dependencies.
- Hot reload: the install, uninstall, enable, disable and upgrade routes call `reconcilePluginSourcesNow`. A changed plugin is redeployed in place (shutdown, cache sweep, init) with no daemon restart. Disabling a plugin writes a `.disabled` sentinel at `<workspace>/plugins/<name>/.disabled` (disabled-state.ts). This also applies to the default plugins in assistant/src/plugins/defaults/*, and it takes effect on the next turn.
- CLI (assistant/src/cli/commands/plugins.ts): install, versions, list, inspect, diff, search, publish, uninstall, enable, disable, upgrade. The logic lives in assistant/src/cli/lib/: install-from-platform.ts, install-from-github.ts, plugin-catalog-*.ts, publish-plugin.ts, upgrade-plugin.ts, toggle-plugin.ts, plugin-pin-history.ts, plugin-fingerprint.ts, and the offline fallback bundled-marketplace.json / bundled-plugin-packages.json.
- HTTP routes (assistant/src/runtime/routes/plugins-routes.ts): GET plugins, plugins/search, POST plugins/install, plugins/:name (GET, DELETE), :name/icon, inspect, versions, diff, upgrade, enable, disable.
- Install pipeline: a plain install by name calls `GET {platform.baseUrl}/v1/plugins/{name}/install/`. That endpoint serves a `.tgz`, which is checked against an ETag sha256 and then extracted. The catalog comes from `GET {platform.baseUrl}/v1/plugins/` (plugin-catalog-platform.ts, falling back to the bundled copy). `--pin`, `--ref`, `--allow-unreviewed` and GitHub URLs take the git path, which only accepts full commit SHAs. There is a consent gate for declared schedules (`confirmStagedOrAbort`).
- Marketplace data: plugins/marketplace.json (a subset of the Claude Code marketplace schema, with GitHub sources pinned by SHA), plugins/mcp-catalog/<vendor>/{plugin.json, mcp.json, icon.png}, plugins/plugin-icons.json, and the generators scripts/plugins/*.mjs and scripts/check-marketplace-prefix.mjs.

Skills:
- Format follows the Agent Skills spec (skills/AGENTS.md): frontmatter `name` and `description`, plus `metadata.vellum` (category, display-name, activation-hints, includes). The first-party list is skills/catalog.json, generated by scripts/skills/generate-catalog.mjs and checked by lint-skill-spec.mjs and check-catalog.mjs.
- Code is in assistant/src/skills/: catalog-install.ts, managed-store.ts (validated ids, writes to `<workspace>/skills/<id>`), install-meta.ts (origin vellum, clawhub, skillssh or custom; contentHash; authorship provenance, where assistant-authored skills can be pruned), remote-skill-policy.ts (moderation and risk thresholds for clawhub and skills.sh), clawhub.ts, skillssh-registry.ts, skill-history.ts, version-hash.ts, tool-manifest.ts (TOOLS.json v1 with risk low, medium or high and execution target host or sandbox).
- How a skill adds tools: tools only register while the skill is active. assistant/src/skills/active-skill-tools.ts scans for `<loaded_skill id version>` markers, and assistant/src/tools/skills/{load.ts, skill-tool-factory.ts, sandbox-runner.ts} do the projection.
- Routes (assistant/src/runtime/routes/skills-routes.ts): skills, categories, search, draft, install, :id/enable, :id/disable, :id/config, check-updates, :id/update, :id/inspect, :id (DELETE). enable and disable write `skills.entries[id].enabled` in the workspace config (assistant/src/daemon/handlers/skills.ts:1145; schema in config/schemas/skills.ts, which also has `skills.load.extraDirs` and `remoteProviders`).
- CLI: assistant/src/cli/commands/skills.ts (list, inspect, search, install for the catalog, uninstall, and `add` for community skills from skills.sh or clawhub).

Tools:
- Registry: assistant/src/tools/registry.ts. assistant/src/tools/AGENTS.md discourages new non-skill tools, and a pre-commit hook blocks them.
- Workspace overrides: `<workspace>/tools/<name>.{ts,js,json}` registers a tool, and a `<name>.removed` sentinel strips a core tool (assistant/src/tools/workspace-tools/loader.ts). Plugins, skills and MCP cannot register over a name the workspace owns. This is the existing mechanism for taking a core tool away from one bot.

MCP:
- Code is in assistant/src/mcp/: manager.ts, workspace-mcp-config.ts (`<workspace>/mcp.json`), effective-config.ts, mcp-oauth-provider.ts, mcp-header-store.ts, reload-signal.ts, tool-caps.ts.
- CLI: assistant/src/cli/commands/mcp.ts (list, reload, add, auth, remove). OAuth routes: runtime/routes/mcp-auth-routes.ts.

Change notifications:
- `sync_changed` tags (assistant/src/daemon/message-types/sync.ts) already include `plugins:list` and `mcp:list`. There is no `skills:list` tag.

Secrets:
- `assistant credentials prompt` (assistant/src/cli/commands/credentials.ts:404) opens a secure input. It exits 0 when the value is stored and 130 when the user dismisses it. The other approved path is `ui_show` with `channel_setup`. Plugins read secrets through `resolveCredential()`, scoped to the plugin name. `assistant ui confirm/request` provide blocking confirmations inside scripts.

(2) SCOPING EXTENSIONS PER BOT

- What happens today: anu/src/sandbox/sessions.ts gives each session `workspaceFor(sessionId) = <root>/<sessionId>`. anu/src/sandbox/drivers/harness.ts then boots CES, the daemon and the gateway for that session with `VELLUM_WORKSPACE_DIR=<ws>/harness/.vellum/workspace` and a per-session protected/CES directory. Everything the harness reads is resolved from `getWorkspaceDir()`: plugins, skills, tools, mcp.json, the config with `skills.entries`, and the `.disabled` and `.removed` sentinels. So a workspace is already a complete isolation boundary.
- What a bot does today: anu/src/sandbox/drivers/bot-profile.ts writes IDENTITY.md, SOUL.md and `.anu-bot-version` before boot. After boot it renders the avatar, adds an inference profile and calls POST /v1/skills/:id/enable, filtered by `BOT_SKILL_IDS`, which is currently empty.
- Recommended model: one bot workspace template per bot, materialized into each session's workspace before boot.
  - Pre-boot, the sandbox fetches the bot's lockfile (extension name, version, sha256) from the registry server. It installs each item into `<ws>/plugins/<name>` or `<ws>/skills/<id>`, verifies the hashes, and writes `.disabled` for default plugins the bot excludes, `.removed` for core tools it excludes, and `mcp.json` plus the config entries.
  - A sidecar like `.anu-bot-version` records which lockfile hash is installed, so a resume skips the reinstall.
  - A content-addressed cache on the sandbox host avoids repeat downloads. Hardlink or copy from it, not symlink: the containment checks use realpath and reject links that leave the plugin root.
- Alternative: one persistent workspace per bot shared by all its sessions. This is simpler, but it breaks the current per-session lifecycle and leaks memory and history between that bot's chats.
- Credentials: CES state is per session today (protected/ under the session root). Bot-level secrets that should outlive a session need either a per-bot protected directory mounted into each session, or an API-side vault that pushes values to CES pre-boot without going through the model.

(3) WHAT THE AGENT CAN ALREADY AUTHOR, AND HOW IT COULD PUBLISH

- skills/plugin-builder/SKILL.md, with references for hooks, tools, skills, mcp, routes, channels, apps and distribution, teaches the agent to scaffold `<workspace>/plugins/<name>` and test it in place (option A is a direct copy, and hot reload picks it up). It also covers adding personal tools, skills and MCP servers straight into the workspace with no manifest.
- assistant/src/tools/skills/scaffold-managed.ts and delete-managed.ts, plus POST skills/draft, let the agent create and delete managed skills at `<workspace>/skills/<id>`. install-meta records that the assistant authored them.
- Publishing today: `assistant plugins publish` (assistant/src/cli/lib/publish-plugin.ts, `runPublish`) validates the package and its git context (SHA, pushed, clean). It then POSTs to the platform registry, which opens a PR against marketplace.json. That route needs GitHub and Vellum's platform, so it does not fit ANU.
- For ANU: replace the publish target with the fourth server. Pack the plugin directory as a tgz, compute its sha256, and POST it to the registry as a draft. The user approves in the app, then the item becomes visible to the user's own registry scope.
  - The low-risk route is to make the registry server implement the same `/v1/plugins/` and `/v1/plugins/{name}/install/` shape (tgz with an ETag sha256) and point `platform.baseUrl` at it per sandbox.
  - Risk: `platform.baseUrl` is also used for other platform calls (auth, telemetry, attribution). Verify those first, or add a separate config key such as `extensions.registryUrl`. That is a small, self-contained change in cli/lib.

(4) GAPS

1. No self-hostable registry. The catalog is a static curated allowlist (marketplace.json) or Vellum's platform, there is no per-user scope, and publishing goes through GitHub PRs.
2. No "bot package" format. Nothing bundles IDENTITY, SOUL, model profile, permissions and a lockfile of extensions.
3. No lockfile or per-bot extension set in the sandbox. `BOT_SKILL_IDS` is empty, and post-boot only enables skills.
4. Skills from a registry have no integrity pin. Plugins carry an ETag sha256 or SHA pins, but skill installs from catalog.json or GitHub do not. There is also no `skills:list` sync_changed tag.
5. No signing or publisher identity. Integrity is a hash only, and author signatures appear only for `vellum.artifact`.
6. Plugins run in-process with the daemon (hooks, tools, routes) and have full `@anu/plugin-api` access, including `resolveCredential` for their own service. Plugins the agent writes need a review gate and a static scan before they are published or installed into another bot. Only skill scripts run in a sandbox (sandbox-runner.ts).
7. Default plugins and core tools can be turned off per workspace (`.disabled`, `.removed`), but nothing records a declared permission set on install. The permission screen would map bot permissions to these sentinels and config entries. It must not add new deterministic approval modes, under Permission controls v2.
8. Credentials are per session. Bot-level secret persistence and a phone-side secure input that pushes to CES (bridging `assistant credentials prompt`) are missing in ANU. The sandbox already relays approvals (`reporter.sessionApproval` in sessions.ts), and the secure input could follow the same path.
9. The new-tool rule means agent-made extensions should be skills (scripts plus SKILL.md, or TOOLS.json inside a plugin skill) or plugin tools in the user's workspace, never core registry tools.
10. Container cost: each session boots a full CES, daemon and gateway. Per-bot install needs a host-side cache to keep cold starts fast.
